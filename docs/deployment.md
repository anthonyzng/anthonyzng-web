# Deployment

Moved from `CLAUDE.md` section 7.

- **Where**: GCP project `anthonyzng-web` (billing linked), VM `anthonyzng-web` in `us-east1-b` (`vm-1` in the Owwsolution platform's inventory): e2-small (2 GiB RAM plus 2 GiB swap), Debian 12, 30 GB standard disk, Shielded VM, network tag `web`; static external IPv4 `anthonyzng-web-ip` = `34.26.232.31`. Firewall (`default` network): `allow-web-cloudflare` (tcp 80, 443, udp 443 from Cloudflare's ranges → tag `web`; the former open `allow-web` is disabled), `default-allow-ssh` (22, key-only logins), ICMP and internal. The owner's gcloud CLI is signed in on the dev machine (`gcloud config`: project `anthonyzng-web`, zone `us-east1-b`); `gcloud compute ssh anthonyzng-web` gives an admin shell.

- **The platform**: `/opt/platform` (the private repo `Owwsolution/platform`, deployed by its own CI to every VM of its inventory): Caddy, PostgreSQL, the nightly dumps, and the scripts this site's deploy uses (`deploy-app`, `install-site`, `provision-app`, `app-hosts`, `restore-app`, `row-counts`). The VM was set up with the platform repo's one-time VM setup script (Docker Engine + Compose plugin, 2 GiB swap, the `local` log driver (10 MB × 3 per container), unattended security upgrades, the `deploy` user (no password, login only with `restrict`ed keys, in the `docker` group, which makes it root-equivalent on the VM: the keys are guarded accordingly), `/opt/platform` and `/opt/apps`). The VM's SSH host key is pinned in the `DEPLOY_KNOWN_HOSTS` secret (ED25519 `SHA256:pY1Yg2Z6ho87hgcoEHiFYYqIpJTOOgtjyLkU7MZa/pY`).

- **Production configuration lives only on the VM**: `/opt/apps/anthonyzng-web/.env` (`DATABASE_OWNER_URL`, `DATABASE_APP_URL`, written by the platform's `provision-app --write-env`) and `/opt/apps/anthonyzng-web/backend/.env` (the production backend settings, `backend/CLAUDE.md` Settings: `APP_ENV=production`, separately generated `JWT_SECRET` / `IP_HASH_SECRET` / `TOTP_ENCRYPTION_KEY`, the admin account, `CONTACT_TO_EMAIL`, `EMAIL_PROVIDER=resend` + `RESEND_API_KEY`, the real `TURNSTILE_SECRET_KEY`, `CORS_ORIGINS=https://owwsolution.com`), mode `600`, owned by `deploy`. The PostgreSQL superuser's password is the platform's (`/opt/platform/.env`) and this site never uses it. They are written on the VM and never pass through GitHub, the repo or a log. The addresses the snippet may serve are registered once on the VM, before the first deploy, with the platform's `scripts/app-hosts set anthonyzng-web owwsolution.com,www.owwsolution.com,api.owwsolution.com` (`install-site` refuses any other host), and the images it may run and re-tag with `scripts/app-images set anthonyzng-web ghcr.io/anthonyzng/anthonyzng-web-` (`deploy-app` refuses any other image, in its arguments and in the compose file). `docker-compose.yml` and `deploy/anthonyzng-web.caddy` are copied there by every deploy.

- **CI/CD** (`.github/workflows/ci-cd.yml`): every pull request and push to `main` runs `frontend` (npm ci, typecheck, lint, test, build), `backend` (uv sync, ruff, format check, mypy, pytest against a PostgreSQL 17 service) and `containers` (the three Compose files parse; `docker-compose.yml` defines exactly `backend`, `frontend` and `migrate` and no service has `build` or `ports`; the Caddy snippet validates inside `deploy/ci/Caddyfile` with production's and the local addresses and is formatted). Every job has a `timeout-minutes` and its checkouts keep no credentials. On `main`, when the repository variable `DEPLOY_ENABLED` is `true`: `images` builds both images with Buildx (GHA cache) and pushes `ghcr.io/anthonyzng/anthonyzng-web-{backend,frontend}` tagged with the commit SHA and `latest` (private packages; the frontend gets the variables `VITE_API_BASE_URL` and `VITE_TURNSTILE_SITE_KEY` as build args), then `deploy` (GitHub environment `production`, one at a time) logs in as `deploy` with the `DEPLOY_SSH_KEY` secret and the pinned host key (host and user names are checked against patterns before anything is written; the SSH options are those of the platform's own deploy workflow: pinned known hosts only, no forwarding, no agent, batch mode), sends `docker-compose.yml` and `deploy/anthonyzng-web.caddy` (regular files inside the workspace, never symlinks), each on stdin to the platform's `/opt/platform/scripts/receive-incoming`, which puts them into `/opt/apps/anthonyzng-web/.incoming/`, and runs the platform's `/opt/platform/scripts/deploy-app` with the job's own `GITHUB_TOKEN` on stdin: GHCR login, this commit's images pulled (`IMAGE_TAG=<sha>`) and tagged `latest` (so every manual compose command on the VM uses the deployed images without a registry login), logout right after the pull, `docker compose up -d --remove-orphans` (the `migrate` service applies migrations first), the snippet validated against the live Caddy config and installed with a reload, unused images removed. Then it smoke-tests `https://api.owwsolution.com/api/v1/health`, `https://owwsolution.com/`, `https://owwsolution.com/admin/login`, the CV download (once one is uploaded; its URL must match `/api/v1/files/<uuid>` before it is fetched) and that `/api/v1/docs` answers 404 (production mode), every request HTTPS-only with a time limit. The org repos of the platform call its reusable workflows; this public repo in a personal account cannot, so it keeps this workflow and runs the same `deploy-app` (keep the SSH and copy steps in step with the platform's `deploy.yml`). Every action is pinned to a commit SHA (the version in a comment); `.github/dependabot.yml` proposes updates weekly: GitHub Actions (one grouped pull request), npm (`/frontend`) and uv (`/backend`) with minor and patch updates grouped per ecosystem and majors one by one, and the container images one by one (the Dockerfiles, and `docker-compose.dev.yml`, where PostgreSQL majors are ignored; Node majors, of the build image and `@types/node`, are ignored too and moved by hand to each new Active LTS together with the workflows' `node-version`). The Caddy image of the CI snippet check follows the platform's (bump them together). Review a major before merging: the images and the deploy run only after the merge. Repository settings: variables `DEPLOY_ENABLED`, `DEPLOY_HOST`, `DEPLOY_USER`, `VITE_API_BASE_URL`, `VITE_TURNSTILE_SITE_KEY`; secrets `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` in the `production` environment only (deployment branch policy: `main`), never at repository level, so no pull request, even one that edits the workflow, can read them. The deploy key exists only in that secret and the VM's `authorized_keys`, where it is this site's APP key, gated by the platform's `scripts/ssh-gate`: `command="/opt/platform/scripts/ssh-gate anthonyzng-web",restrict <key>` (no shell, scp, sftp, forwarding or pseudo-terminal; it can only send this site's two files with `receive-incoming` and run `deploy-app --app anthonyzng-web`; the platform's CLAUDE.md section 7); the platform's own deploys use a separate key. To rotate it (last: 2026-09-25): generate a new pair, add it on the VM with `sudo /opt/platform/scripts/add-app-key anthonyzng-web "<new public key>"` (the old key's line stays until removed), set the environment secret, run a deploy, remove the old line, and never keep the private key on disk.

- **DNS**: the zone `owwsolution.com` on Cloudflare (nameservers `adele.ns.cloudflare.com`, `owen.ns.cloudflare.com`; registrar Namecheap): A records `@`, `www`, `api` → `34.26.232.31`, proxied. Email: Resend's domain records (SPF / DKIM / return path) for `owwsolution.com`, DNS-only, so mail from `noreply@owwsolution.com` is accepted.

- **Cloudflare** (Phase 8): the free plan; SSL/TLS Full (strict) (Flexible would loop: Caddy redirects HTTP to HTTPS), Always Use HTTPS, minimum TLS 1.2; Rocket Loader and Email Address Obfuscation off (both rewrite pages with inline scripts the CSP refuses); Web Analytics with automatic setup. The platform's Caddy takes the visitor's address from `CF-Connecting-IP` only for requests from Cloudflare's ranges, and the GCP firewall admits HTTP(S) from Cloudflare only (`allow-web-cloudflare`, Cloudflare's IPv4 ranges from https://www.cloudflare.com/ips-v4, to tag `web`; the VM has no IPv6); when Cloudflare announces new ranges, update both this rule and the platform Caddyfile's `trusted_proxies`. The platform's Caddy holds the Let's Encrypt certificates (copied from the site's earlier Caddy at the move, so none was re-issued) and renews them through Cloudflare: the HTTP challenge is redirected to HTTPS at the edge, and Caddy answers ACME challenges on its HTTPS server too (check the renewal in late November, 30 days before 2026-12-24; a one-off scheduled Claude task on the owner's machine runs that check on 2026-11-28, looking at the platform's `caddy` service in `/opt/platform`). Caching: pages and API answers pass uncached (`DYNAMIC`); hashed `/assets/*` are cached at the edge (new names on every deploy); Browser Cache TTL must be "Respect Existing Headers" (Cloudflare's default 4 h would override the origin's `no-cache` on `robots.txt`, `theme-init.js`, the share image).

- **Backups**: the snapshot schedule `anthonyzng-web-daily` (resource policy in `us-east1`, attached to the boot disk `anthonyzng-web`) snapshots the whole disk every day at 19:00 UTC, kept 7 days (`keep-auto-snapshots` if the disk is deleted, stored in `us-east1`); a snapshot is crash-consistent, which PostgreSQL recovers from like a power cut. In addition the platform dumps `anthonyzng_web` every night at 18:30 UTC into `/opt/platform/backups/anthonyzng_web/` (kept 7 days, same disk: a convenience for restoring this database alone, `scripts/restore-app`). Restore a whole disk: create a disk from a snapshot (`gcloud compute disks create … --source-snapshot …`) and swap it in as the VM's boot disk, or attach it to read the volume under `/var/lib/docker/volumes/`. `gcloud compute snapshots list` shows them.

- **Operations** (on the VM, `cd /opt/apps/anthonyzng-web`, as `deploy` or with sudo; type each command on its own, and never pipe a list of them into `ssh <vm> bash -s`: a `docker compose run` or `exec` reads stdin and would swallow the lines after it, hence `</dev/null` on the ones below): `docker compose ps`, `docker compose logs -f backend`; roll back by re-running the deploy job of an older commit (Actions → the run → Re-run jobs); turn two-factor sign-in off (a lost phone) with `docker compose run --rm -T backend python -m app.admin_totp reset </dev/null`; seed an empty database once with `docker compose run --rm -T backend python -m app.seed </dev/null`; rotate the database passwords with the platform's `scripts/provision-app anthonyzng-web --scheme postgresql+asyncpg --write-env /opt/apps/anthonyzng-web/.env`, then `docker compose up -d`. The proxy and the database are operated from `/opt/platform` (the platform's `CLAUDE.md`). The admin panel is the source of truth; after editing content, merge the *Content snapshot sync* pull request (daily), or run that workflow now.

- Run exactly one uvicorn worker (the rate limiter is in-process) without an access log; both are fixed in the backend image (`docs/containers.md`). The Content-Security-Policy must allow the API origin in `connect-src` and `img-src` (project cover images are served by `GET /files/{id}`).
