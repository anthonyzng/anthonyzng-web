# Frontend: content

Moved from `CLAUDE.md` section 6.1.

- **Content**: the database, edited in the admin panel, is the source of truth for the page content of the hero (eyebrow, name, roles), "In brief", Experience, Projects, Skills, Tools, Contact and Archive (the storage model is in `CLAUDE.md` section 5; proper nouns stay untranslated, descriptive chips are translated terms, so no English phrase survives on the Chinese page). The sections render `ResolvedContent` (`src/content/resolved.ts`), exactly the `GET /content` payload of one locale. The static fallback is that payload saved per locale, `src/content/snapshot/{en,zh-Hant}.json`, bundled and returned by `staticContent(locale)` (`staticContent.ts`). `npm run content:sync` (`frontend/scripts/sync-content.mjs`) rewrites both files from a running API (default `http://localhost:8000`, else `VITE_API_BASE_URL` or `npm run content:sync -- <origin>`; `-- --api <origin>` works too, and Windows PowerShell drops the `--`, so the bare origin is accepted); it fetches and checks both locales (fetching once more if their untranslated facts disagree, i.e. an admin save landed in between), writes both to temporary files and renames them into place, so a failure leaves the previous pair untouched. File links (cover images, the CV) are ids in the database behind that API, so sync from the API of the database the site will use (production before a deploy; the script notes a local origin). The *Content snapshot sync* workflow (`.github/workflows/content-sync.yml`) runs it against production every day at 04:23 UTC (and on demand from the Actions tab) and, when the files change, runs the snapshot test and the typecheck and opens or updates a pull request from `bot/content-sync` (and closes it when main already matches the API, so an outdated one is never merged) (a pull request opened by GitHub Actions starts no CI, hence its own checks; it needs the repository setting "Allow GitHub Actions to create and approve pull requests"); merging it deploys the new snapshot. To update at once, run the workflow or the script and commit the two files; a stale snapshot only means the first paint shows the old content until the API answers. `snapshot.test.ts` validates both files with the same zod schema as a live response, key for key (an extra key would make every identical API answer look new), and checks that both locales carry the same items in the same order with the same untranslated facts; no test depends on what the snapshot says (the other tests render the fixed fixture `src/test/contentFixture.ts`, see `docs/frontend/api-client.md`). Only layout copy stays under `content.*` in the locale files (`locales.test.ts` pins the list): `content.techOf`, `content.experience.present`, `content.projects.{note,visit,placeholder.*}`, the `content.skills.credentials.*` labels and the in-progress suffix, `content.contact.labels.{cv,location}`, `content.contact.cvDownload`. Dates are stored once, as `YYYY-MM`, and the visible label is formatted per locale (`src/i18n/formatMonth.ts`), so `<time datetime>` and the label can never drift apart. Projects: a `placeholder: true` project is a reserved slot (badge, generic copy, never an image); the "being written up" note shows only while a slot remains (or there is no project); a real project's cover image (`image`, uploaded in the admin panel) fills the card's parallax plane over the hatch (`<img alt="">` with `object-cover`, lazy, decorative because the title and summary say what it is, keyed by its URL); an image that fails to load hides itself and leaves the hatch, never an empty frame. Contact: the channels (email, LinkedIn, GitHub, approved for publication by the owner) are content rows; once a CV is uploaded, a CV row with a download link (`Download CV (PDF, 180 KB)`, size from `src/i18n/formatFileSize.ts`) follows the channels. Experience: `companyUrl` (set in the admin panel, optional) makes the company name a link to the employer's website (new tab); a value the browser cannot parse becomes null like a project link. Skills: a school's or certification's `url` (optional) links its name the same way (`ExternalLink`). Tools (`sections/Tools.tsx`, numbered chapter 04 after Skills, `id="tools"`): `ToolCard` per tool (kind in the accent, number, name, summary, chips, an "Open tool" cue), the name's link stretched over the card (new tab), the chips above it; `content.tools.empty` while there is none. Archive (`sections/Archive.tsx`, `id="archive"`, after the closing screen, on the same ink): one row per entry (month, kind, title, optional summary), each row a link in a new tab; no nav link and no number, in `LANDING_IDS` only, and left out while empty. `content.tools.{empty,open}` are layout copy (pinned in `locales.test.ts`). Hero and "In brief": `hero` (`eyebrow`, `nameFirst`, `nameLast`, `roles`) and `statement` (`label`, `intro`) come from the site texts `hero_eyebrow`, `hero_name_first`, `hero_name_last`, `statement_label`, `statement_intro` and the `hero-roles` collection (added, removed and ordered in the admin panel); the statement's visual copy is keyed by language and text, and `useStatementReveal` takes the text as a dependency, so a newer paragraph from the API gets a fresh SplitText split. The SEO copy (`meta.*`, `index.html`, the share image, the JSON-LD) stays in code by the owner's choice: update it by hand when the roles change for good. File URLs in the payload (`image.url`, `cv.url`) are root-relative paths on the API origin; `fileUrl()` (`src/api/files.ts`) prefixes `API_BASE_URL`.
