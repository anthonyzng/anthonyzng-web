# Backend: admin API

Moved from `CLAUDE.md` section 6.2.

- **Admin API** (`api/v1/admin.py`; every route needs the admin session, runs `require_trusted_origin` and answers `Cache-Control: no-store`): `GET /admin/summary` (items per collection, unread messages, the CV). Content collections are addressed by URL segment through the registry in `services/collections.py` (`hero-roles`, `experience`, `projects`, `skill-groups`, `education`, `certifications`, `languages`, `tools`, `contact-links`, `archive`, `site-texts`), which pairs each model with its write model (`*In`, `schemas/content_write.py`), its read model (`*Out` = the write model plus read-only `updatedAt`, and `image` on projects; `sortOrder` always present) and the row mapping the seed shares. `GET /admin/content/{collection}` → `{"items": [...]}` in both locales, in display order; `POST` (201, 409 `conflict` on a taken slug, 422 on `slug` for `new`, the admin panel's create route); `PUT …/{slug}` (full replacement; the slug is immutable, another one in the body is 422 on `slug`); `DELETE …/{slug}` (204; a project's cover image file goes with it); `POST …/reorder` `{"slugs": [...]}` (every slug exactly once, else 422 on `slugs`; rewrites `sort_order` to 0..n-1; `site-texts` has no order, 404). The order belongs to the server: `sortOrder` is optional in the write models and the admin panel never sends it; a new row without it is placed by the server (an experience entry by chronology, current roles first and then the latest `start` first, the rows after it moving down one; anything else after the last), an update without it keeps the stored order, and order changes (placement, reorder) and cover image changes never touch `updated_at`, which stays the version of the row's editable content. Optimistic concurrency: a `PUT` may carry `If-Match: "<updatedAt>"` (the version it was edited from, as the API returned it); the row is locked, and if its `updated_at` differs (or the header is not one aware timestamp) the answer is 412 `precondition_failed` and nothing is saved; `*` or no header skips the check. Bodies are validated against the collection's write model inside the handler and keep the 422 envelope with dotted `fields` keys (`translations.zh-Hant.role`, `tech.2`; `body` for rules across fields); the `Tag` validator reports one error per chip, on its list index. Input validation spells out ASCII (`[0-9]`: Pydantic's regex engine would take any Unicode digit for `\d`), bounds `sortOrder` to int4 and message ids / `offset` to the database's ranges, and accepts a project `url` only when a browser could parse it (scheme http(s), a host without forbidden characters, a valid port, no whitespace). Project cover image: `PUT /admin/content/projects/{slug}/image` (multipart, field `file`) and `DELETE …/image`, both answering the project (`ProjectOut`); a placeholder takes no image (422 `image_placeholder`), and a project with an image cannot become a placeholder (422 on `placeholder`). CV: `GET`, `PUT` (multipart `file`), `DELETE /admin/cv`, all answering `{"cv": {...} | null}`. Upload refusals are 422 with the specific codes listed under API surface (`backend/CLAUDE.md`). Messages: `GET /admin/messages?status=all|unread&limit=1..100&offset=0..&asOf=<iso>` → `{items, total (for the filter), unread (overall, live), asOf}`, newest first: the set is taken as it was at `asOf` (now when absent, and the response says which instant it used), leaving out later messages and, in the unread view, still counting messages read after it, so the later pages of a view that pass the first page's `asOf` never shift when messages are read or arrive; an item carries `source` (the 12-character fingerprint of the IP hash, never the hash itself), `userAgent`, `deliveryStatus` / `deliveryError` and `readAt`; `PATCH /admin/messages/{id}` `{"read": bool}` (reading again keeps the first read time); `DELETE` (204). An upload is read inside the handler, after the auth dependencies (`read_upload`), never as a FastAPI form parameter, which would be parsed before authentication.
